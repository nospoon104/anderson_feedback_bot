
# Архитектура

Проект использует слоистую backend-архитектуру, в которой Telegram-слой, бизнес-логика и работа с базой разделены по отдельным уровням.

Базовый поток выглядит так:

`Telegram update -> handler -> service -> repository -> PostgreSQL`

Такой подход хорошо подходит для MVP: код остаётся читаемым, бизнес-логика не размазывается по Telegram-обработчикам, а работу с данными можно развивать отдельно.

## Слои приложения

### 1. Handlers

Расположение: `app/bot/handlers/`

Отвечают за:

- приём Telegram updates;
- проверку пользователя и роли;
- управление FSM-сценариями;
- вызов сервисов;
- отправку сообщений, документов и клавиатур.

Handlers не содержат тяжёлую бизнес-логику и не работают с SQL напрямую.

### 2. Services

Расположение: `app/services/`

Отвечают за:

- бизнес-правила приложения;
- валидацию прикладных ограничений;
- расчёт аналитики;
- координацию работы репозиториев;
- подготовку данных для отчётов и экспорта.

Основные сервисы:

- `AuthService`
- `SurveyService`
- `ReportService`
- `ExcelReportService`
- `AICommentService`

### 3. Repositories

Расположение: `app/db/repositories/`

Отвечают за:

- доступ к PostgreSQL;
- выборки и сохранение сущностей;
- изоляцию persistence-логики от прикладного кода.

Основные репозитории:

- `UserRepository`
- `CafeRepository`
- `SurveyRepository`

### 4. Database models

Расположение: `app/db/models/`

Содержат ORM-модели SQLAlchemy и описывают структуру таблиц и связи между сущностями.

Основные модели:

- `Cafe`
- `User`
- `Survey`

### 5. Schemas

Расположение: `app/schemas/`

Содержат Pydantic-схемы, которые используются для структурирования данных на уровне приложения, отчётов и обмена между слоями.

## Пример сценария: ввод анкеты

1. Менеджер нажимает `Добавить анкету`.
2. Handler запускает FSM-сценарий.
3. Бот по шагам запрашивает:
   - дату и время визита;
   - номер стола;
   - 4 ответа `Да / Нет`;
   - комментарий или пропуск.
4. Handler определяет пользователя по `telegram_id`.
5. `SurveyService` валидирует данные и бизнес-ограничения.
6. `SurveyRepository` сохраняет анкету в PostgreSQL.
7. Бот отправляет подтверждение пользователю.

## Пример сценария: формирование отчёта

1. Пользователь выбирает тип отчёта.
2. Handler получает период через FSM.
3. `ReportService` загружает анкеты через репозиторий.
4. Сервис рассчитывает:
   - общее количество анкет;
   - средний балл;
   - средний процент;
   - статистику по вопросам;
   - распределение итоговых оценок;
   - сравнение с предыдущим периодом.
5. Для отчёта по кафе дополнительно выполняется AI-анализ комментариев.
6. Handler отправляет текстовый отчёт и Excel-файл.

## Почему такая архитектура подходит проекту

Плюсы текущего подхода:

- Telegram-слой не смешан с SQL;
- бизнес-логика сосредоточена в сервисах;
- отчётную часть удобно развивать отдельно;
- код подходит не только для локального прототипа, но и для рабочего MVP.

## Текущие ограничения

На текущем этапе проект осознанно остаётся достаточно простым:

- сессии создаются напрямую в handlers;
- нет DI-контейнера;
- нет централизованного middleware для ошибок;
- нет развитой observability-инфраструктуры;


Для рабочего MVP это допустимо, а дальнейшие улучшения можно добавлять постепенно.

## Возможные дальнейшие улучшения

- вынести фабрики сервисов и репозиториев;
- добавить централизованную обработку ошибок;
- улучшить логирование;
- покрыть ключевые сервисы тестами;
- выделить dev/admin scripts в отдельную директорию;
- при необходимости перейти на webhook-режим.
