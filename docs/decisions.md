# Ключевые решения по проекту

Этот документ фиксирует основные технические и продуктовые решения, принятые в проекте на стадии MVP.

## 1. Telegram-бот как основной интерфейс

Решение: использовать Telegram как основной интерфейс для сотрудников.

Почему:

- позволяет быстро доставить MVP;
- не требует отдельного web frontend;
- снижает порог входа для менеджеров;
- хорошо подходит для внутреннего инструмента.

Компромисс:

- UX ограничен форматом чата;
- многошаговые сценарии требуют FSM;
- сложные отчётные интерфейсы в Telegram менее удобны, чем в web UI.

## 2. Ручная оцифровка бумажных анкет

Решение: менеджеры переносят бумажные анкеты в систему вручную.

Почему:

- это самый быстрый способ запустить цифровой контур поверх существующего процесса;
- не нужно ломать офлайн-процесс сбора обратной связи;
- можно быстро начать копить данные для аналитики.

Компромисс:

- ручной ввод остаётся частью процесса;
- есть риск человеческих ошибок;
- antifraud-механики не входят в MVP.

## 3. PostgreSQL как основное хранилище

Решение: использовать PostgreSQL как system of record.

Почему:

- реляционная модель хорошо подходит для анкет, пользователей и отчётов;
- удобно делать агрегации и выборки по периодам;
- решение подходит и для MVP, и для дальнейшего роста.

Компромисс:

- инфраструктурно сложнее, чем локальное файловое хранение;
- требуется настройка окружения и миграций.

## 4. Async stack на Python

Решение: использовать `aiogram 3`, `SQLAlchemy 2 async` и `asyncpg`.

Почему:

- стек согласован по async-модели;
- хорошо сочетается с Telegram-ботом;
- даёт современную техническую базу для развития проекта.

Компромисс:

- код и отладка немного сложнее, чем в синхронном варианте;
- требуется аккуратная работа с сессиями и зависимостями.

## 5. Слоистая архитектура

Решение: разделить проект на `handlers`, `services`, `repositories` и `db/models`.

Почему:

- бизнес-логика не размазывается по Telegram-handlers;
- доступ к БД остаётся изолированным;
- отчётную логику проще поддерживать и расширять;
- проект легче читать и сопровождать.

Компромисс:

- появляется больше файлов и немного шаблонного кода;
- для маленького скрипта это было бы избыточно, но для рабочего MVP — оправданно.

## 6. Простая ролевая модель

Решение: оставить на старте две роли: `manager` и `superuser`.

Почему:

- этого достаточно для текущих сценариев;
- проще валидировать права доступа;
- удобно объяснять и тестировать.

Компромисс:

- пока нет гранулярной системы permissions;
- административные сценарии ограничены.

## 7. Сравнение с предыдущим периодом

Решение: каждый отчёт сравнивает выбранный период с предыдущим периодом той же длины.

Почему:

- это простая и понятная метрика для операционного управления;
- не требует отдельной BI-системы;
- помогает быстро оценивать динамику.

Компромисс:

- при малом объёме анкет сравнение может быть шумным;
- логику сравнения нужно явно фиксировать в документации.

## 8. Excel как основной формат выгрузки

Решение: генерировать `.xlsx`-отчёты на стороне сервера через `openpyxl`.

Почему:

- Excel остаётся привычным форматом для менеджеров и руководителей;
- файлы удобно отправлять и использовать вне системы;
- это практичный формат для внутренней отчётности.

Компромисс:

- оформление отчётов требует отдельной логики;
- поддержка экспорта усложняет кодовую базу.

## 9. AI-анализ комментариев как надстройка над отчётным ядром

Решение: AI используется не как основная функция продукта, а как дополнительный аналитический слой поверх уже собранных комментариев.

Почему:

- ключевая ценность продукта — в сборе и структурировании данных;
- AI даёт дополнительную интерпретацию, но не заменяет саму отчётность;
- такой подход снижает риск, если внешний AI-сервис временно недоступен.

Компромисс:

- ценность AI зависит от качества и объёма комментариев;
- требуется fallback-логика на случай ошибок внешнего API.
