# Схема базы данных

Проект использует PostgreSQL как основное хранилище данных.

Текущая схема намеренно сделана компактной: для рабочего MVP достаточно трёх основных сущностей:

- `cafes`
- `users`
- `surveys`

Такой дизайн покрывает текущую задачу: хранение анкет по сети ресторанов, разграничение доступа по ролям и построение отчётов по кафе и по всей сети.

## Таблица `cafes`

Хранит список кафе сети.

Основные поля:

- `id` — первичный ключ;
- `name` — название кафе;
- `code` — уникальный код кафе;
- `address` — адрес;
- `is_active` — признак активности;
- `created_at` — дата создания записи.

Связи:

- одно кафе связано со многими пользователями;
- одно кафе связано со многими анкетами.

## Таблица `users`

Хранит пользователей Telegram, которые имеют доступ к боту.

Основные поля:

- `id` — первичный ключ;
- `telegram_id` — уникальный Telegram ID;
- `full_name` — имя пользователя;
- `role` — роль (`manager` или `superuser`);
- `cafe_id` — привязка к кафе, если пользователь является менеджером;
- `is_active` — признак активности;
- `created_at` — дата создания записи.

Бизнес-правила:

- менеджер должен быть привязан к кафе;
- суперпользователь может не иметь `cafe_id`;
- доступ к функциям определяется ролью.

## Таблица `surveys`

Хранит оцифрованные анкеты гостей.

Основные поля:

- `id` — первичный ключ;
- `cafe_id` — кафе, к которому относится анкета;
- `created_by_user_id` — пользователь, который внёс анкету;
- `visit_datetime` — дата и время визита;
- `table_number` — номер стола;
- `q1`, `q2`, `q3`, `q4` — ответы на 4 yes/no вопроса;
- `comment_text` — необязательный комментарий гостя;
- `created_at` — дата создания записи.

Бизнес-правила:

- анкета всегда принадлежит конкретному кафе;
- анкета всегда имеет автора;
- ответы на вопросы хранятся как boolean-значения;
- комментарий является необязательным.
